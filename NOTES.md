## Phase 1 — Skeleton and schema

**What changed**

- `git init` (repo did not exist on arrival; the plan mandates commit-per-phase, so a
  repo is a precondition).
- Root scaffolding: `.gitignore`, `.env.example`, `docker-compose.yml`.
- `api/`: FastAPI app (`/health`), SQLAlchemy models for every table in §3, Alembic
  migration `0001` creating the full schema + `pgvector` extension, a seed script that
  loads 3 sources, and a placeholder polling worker.
- `web/`: Next.js (App Router, TS, Tailwind) with a single page that lists sources from
  the API.
- Two trivial tests so `pytest` runs.

**Decisions**

- **UUID primary keys** (`gen_random_uuid()`), not serials. It's a public demo link
  (Phase 9); non-enumerable IDs are one less thing to think about, and UUIDs read as
  production-shaped.
- **Text columns + CHECK constraints** for the enum-ish fields (`direction`, `status`,
  `due_precision`, `state`, `jobs.status`, `sources.kind`) rather than native Postgres
  ENUM types. Native enums make later `ALTER` painful; a demo iterates on its own
  vocabulary. CHECKs give the same integrity with none of the migration friction.
- **Alembic** for migrations (matches a real FastAPI shop), but migrations are
  hand-written, not autogenerated — I want explicit control over the `pgvector`
  extension and the CHECK constraints.
- The `commitments.what_embedding vector(1536)` column is **deferred to the Phase 4
  migration**, since embeddings are a Phase 4 concern and §3 doesn't list it. Keeping
  Phase 1's schema faithful to §3.

**What surprised me**

- Host ports 3000 and 8000 were already occupied by other local dev processes on the
  build machine, so I remapped the published ports to **web=3001, api=8001** (container
  ports unchanged at 3000/8000). Killing a stranger's processes to claim a port is not
  my call to make; remapping is non-destructive and reversible. `NEXT_PUBLIC_API_BASE`
  moved to `:8001` to match. Documented in `.env.example`.
